# 主体能力库、场景 Bundle 与六节点执行契约

状态：设计提案，供产品与工程评审。适用于单张 RGB 图像。示例设备、配置版本与规则均为设计样例。

## 1. 三方各维护什么

| 层 | 唯一维护的内容 | 向下游交付 |
|---|---|---|
| Web 能力库 | 主体类别、独立版本的 Question 和 Tool、违规类别目录；Check 对证据与类别的业务约定 | 已发布算法修订及能力版本，沿用 Publication、精确 Build 或联合计划 |
| 场景配置 | 哪些来源在这个场景承担哪些 Check；各来源怎样取证；可共享哪些工作；模型、工具、规则、资源的精确绑定 | 单个可独立验证的场景 Bundle，附来源与逐 Check 映射 |
| Runtime | 解析指定版本、选择拍摄来源分支，构造本图的检查义务，按六节点执行并记录结果 | 指向原 Check 和类别的任务结果、组级证据、未完成原因 |

业务人员从主体类别进入维护。场景负责人选择已经发布的检查项。运行环境从已接纳、已激活的 Release 取配置。一次 Execution 处理单一来源的一张图，多个来源可共用同一版 Bundle。

## 2. Web 能力管理

**主体类别**是目录入口。一个主体下可以先登记零散的 Question、Tool，暂时没有 Check 消费也可以保存。工具实现若通用于多个主体，通过适用主体关联展示同一个正式条目；使用次数与版本独立。

| 记录 | 建议必填信息 | 关系 |
|---|---|---|
| Question | 稳定 ID、版本、适用主体、用途、上下文依赖、主 Fact 的类型契约与模板引用 | 一项 Question 产生一个主 Fact，可被多个 Check 引用 |
| Tool | 稳定 ID、版本、适用主体、实现引用、输入输出 Schema、可产出的 Facts、坐标或单位约束 | 一个 Tool 可产出多类 Facts；多个 Check 可复用它的实现与输出 |
| 违规类别 | 稳定业务编码、中文名称、定义及版本 | 推荐一个原子 Check 对应一个主类别，同一类别允许多项 Check；整张图可命中多个类别 |
| Check | 稳定 ID、修订、主体、主类别引用、业务适用条件、Question/Tool 引用、各证据用途及必需性、判定口径与缺证据口径 | 草稿可用描述和样例讨论。可执行发布还须绑定确定性 Rule 和生产路径；一个 Check 可以经多条 Rule 实现 |

“本 Check 是否必需某项证据”保存在 Check 的引用关系上。共享 Tool 本身不决定哪项业务一定要用它。违规类别编码用于结果归类；覆盖统计保存完整 Check 清单，同类命中去重仍保留各 Check/Rule 来源。业务确认“什么算违规”，工程人员在同一资源的绑定视图维护类型、版本、模型、坐标和映射。

现有 Web Question 已带 subject_id；Tool 则有 owner_check_id，编译逻辑还需审查所有者校验。建议采用新契约版本：以独立工具能力及 Check→Tool 使用关系承载共享；保留旧 Tool 与原 Check 的来源关联，把旧关系显式迁移为一条使用记录。旧资源即使同名，也不自动去重。旧算法卡及其冻结 Build 继续可读。分类编码、分组策略和类型化输出均需确认后再用于可执行发布；具体问答内容另行设计。

## 3. 场景 Bundle 的作者视图

场景装配复用已有 Web 资源、Runtime 能力绑定和确定性规则。下例仅展示对象关系，短名表示将被解析并锁定的引用。它是建议的作者格式，现有加载器尚无此顶层 YAML 契约。

```yaml
scene: street_parking
version: 1.0.0
input: single_rgb_image

checks:
  blind: check.obstruct_tactile@2
  bay: check.outside_parking_bay@1

sources:
  - id: east_fixed_camera
    match: {source_kind: fixed_camera, camera_id: CAM-017, point_id: P-017}
    checks: [blind, bay]
    profiles: [nonmotor_fixed_view@1]
    geometry:
      tactile: east_camera_tactile@3
      parking_bay: east_camera_parking_bay@2

  - id: patrol_capture
    match: {source_kind: patrol_camera, capture_profile: approved_patrol_rgb}
    checks: [blind]
    profiles: [nonmotor_mobile_view@1]
    geometry:
      tactile: current_frame_tactile_segmentation@1
```

上例明确巡拍来源只承担盲道检查。若业务要求巡拍同时检查停车标线，应把 bay 加入其义务并补齐相机姿态变换、点位资源或本图标线提取方案；必需来源不可提供时给出配置诊断。不得在发布或运行时因为缺资源而从清单偷偷删除 bay。设备覆盖矩阵属于场景配置，Check 原始语义只在 Web 维护一次。

**设备目录与场景策略分工。** 设备身份、点位、相机和可信元数据来源归设备登记或适配层；Bundle 固定本场景采用的字段 Schema、匹配规则、相关资源版本及覆盖。大量相同设备可按已登记的拍摄档案匹配，点位私有几何须锁定到具体视角。移动设备不能仅凭点位相同套用固定相机的像素多边形。请求只提交原图和经接入层校验的来源上下文，不允许提交自选 Rule、模板或 Check 集合覆盖场景合同。

**来源选择建议采用互斥匹配。** 选择在已锁定场景 Release 内进行，N01 固定输入快照后、Pre-N02 Profile 资格判断前完成，沿用工作流内部检查。恰好一条命中才形成来源分支。发布前拒绝可判定的重叠匹配；运行时多匹配记录配置冲突，未知来源记为未支持，缺少必需识别字段记为输入待补齐。这三种情形均应在开始推理前给出原因。新设备不能靠列表顺序意外继承另一设备的策略。匹配限定为精确值或来自锁定目录的有限集合，便于静态检测。

**作者视图与机器包。** 适配器从项目范围内经校验的精确 Build 读取已发布定义，为每个来源编译其有效配置：Profile、Context/Applicability、ModelBinding、Prompt、ToolPlan、FactProducer、RuleSet、几何资源。共享的不可变资源只入包一次。第一版需要为来源匹配表、逐来源 Check 义务和 Check→Rule/类别追溯设计显式的版本化表示；优先复用现有契约能承载的字段。若需扩展 manifest 或 inventory，应同步升级编译器、验证器、加载器和兼容版本；遇到未知必需语义拒绝接纳。机器执行所需的映射必须受 Bundle 完整性保护。Web 导航链接可保存在由摘要关联的外部回执中。执行不依赖实时访问 Web。

## 4. 六节点如何消费配置

| 时点 | 读取或执行 | 可核验的交付 |
|---|---|---|
| 接入、N01、前置检查 | 锁定 Release/Bundle、图像和可信拍摄上下文；解析唯一来源，列出其已配置的 Check 与 Profile，再评估适用性 | source 配置标识、上下文快照、预期义务、排除与未解决原因 |
| N02 | 在合格 Profile 中识别主体；按策略保留有效问题。规则必需的观察有可靠生产路径 | 命中、有效问题清单或 no_hits；无命中保留覆盖缺口 |
| N03 | 按 Profile 定位，依该拍摄方式的邻近分组策略生成每组单红框图 | 每组 object_ref、成员和原图坐标、标记图引用；携相同身份派发到 N04、N05 |
| N04 / N05 | N04 每组一次联合观察、逐题校验。N05 执行预绑定计划；只等待步骤声明的 N04 Fact，其他步骤可先运行 | 逐题主 Facts、工具 Facts、证据引用和失败/受阻原因 |
| N06 | 按 execution_id 与 object_ref 汇合，沿 Profile→RuleSet→Rule 的适用性顺序处理；全扫适用必查规则，保留所有有效命中 | 每项 Check 的状态、类别及证据；整图类别去重及覆盖。G1 只表示同组，“同一辆车多条件命中”仍为后续改进 |

同一来源内，只有主体、定位及分组策略、观察与工具契约、上下文权限相容时才共享工作。共享计算仍保留 Check 各自的证据义务。不同来源、不同 Execution 的观察不合并。

逐 Check 结果建议作为版本化投影，由对象级 Decision、逐条规则记录及 ExecutionCoverage 汇总生成：任何相关组有效命中即保留该 Check 的违规；同时仍有缺口则记录部分覆盖。无有效命中且有未完成义务时显示不确定；所有适用必需义务完整为假时才显示检查未命中。没有观察组也要输出对应的覆盖原因。

结果读取建议提供两个视图：按图查看类别与覆盖；按原卡查看每项 Check 的来源、状态、Rule、object_ref、证据或缺口。至少区分“该来源未配置此项”“适用性有依据地排除”“适用但缺证据”“完整检查未命中”“有效命中”。完整证据下才可作确定性否定，部分覆盖仍保留已确认违规。

## 5. 交付、兼容与验收

第一步以冻结的 Web 样本做离线适配，建立精确 Build／Check／能力 → 转换资产／规则／类别的映射；上游 Build 摘要与每份转换资产的字节摘要分别记录。第二步实现来源契约的编译与加载，用固定照片执行端到端回放。第三步接回现有 /algorithms、/registry、/builds，使业务可预览和追溯。保持草稿、需求发布、候选编译、Runtime 接纳、Release 激活各自的状态。部署策略变动生成新候选；在途执行继续使用原 Release。

| 场景验收样例 | 可观察的预期 |
|---|---|
| 同一个接地点 Tool 被两项 Check 引用 | 能力库只维护一个正式工具版本，保留两条消费关系；修改版本可列出受影响的 Check |
| 固定相机、巡拍拍摄相似画面 | 同一 Bundle 分别选中指定来源；前者运行两项检查，后者一项；输出能解释差异 |
| 固定相机两项检查共享同一 G1 | 兼容配置下一次定位、每组一次联合观察；两项 Check 独立判定，可同时命中两个类别 |
| 已配置标线核验，运行时边界读取失败 | 标线检查受阻，盲道检查继续。若盲道命中，整图返回违规并标记部分覆盖 |
| 未知设备、匹配重叠、主体发现无命中 | 分别显示来源未支持、配置冲突、发现覆盖缺口；三者都不输出确定无违规 |
| 映射缺失或必查 Rule 没有 Fact 生产者 | 发布预检定位到来源分支、原 Check、资源与版本；禁止将不完整候选激活 |
| 同图不同 Release 重放、Web 暂不可达 | 每次按自己的 Bundle 摘要和来源配置解释，旧结果可回查对应原件；运行不向在线作者服务取配置 |

首版建议作两项产品约定供确认：每个原子 Check 一个主违规类别；同一场景允许对不同拍摄来源明确声明不同 Check 清单。若场景约定所有设备承担相同义务，则统一该清单，仅区分取证方式和缺证据处理。
