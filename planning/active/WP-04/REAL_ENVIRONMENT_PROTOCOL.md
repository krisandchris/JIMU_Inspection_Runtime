# WP-04 真实环境验收协议

**当前状态**　真实 RTX 4090 容量、故障恢复、remote-primary Provider 联调均为 `RUNTIME_NOT_RUN` / `UNVERIFIED`。本地已用回环 HTTP 验证精确路由、序列化、超时、限流、截断和取消，并用隔离 PostgreSQL 验证派发与迟到审计。CPU 真进程验收覆盖双进程资源竞争、子孙进程回收和旧租约隔离。GPU 共用额度与 Provider 终态证明在本地使用合成配置。协议编制仅为 `STATIC_REVIEW_ONLY`，无新增实测。[HTTP 证据](W4_2_HTTP_EVIDENCE.md) · [资源证据](../../implementation_evidence/WP-04/W4.4_RESOURCES.md) · [派发预检](../../implementation_evidence/WP-04/independent/PREFLIGHT.md)

## 1. 开跑前登记并签核

| 签核人 | 必填记录 |
|---|---|
| 宿主负责人 | 目标宿主和 GPU UUID、维护窗口、操作者、隔离 Compose 项目及存储、允许的压力与故障动作、停止和恢复负责人。另行登记重启、迁移或现网接入权限。 |
| Provider 和预算负责人 | 固定 HTTPS 目标、账号与地域、批准的部署和能力、凭据作用域、调用窗口、速率和物理请求上限、token 和支出上限、价格表版本及币种、供应方在途终态证明来源。缺版本时登记授权版本证明及生效范围。 |
| 数据与模型权利人 | 输入样品清单与摘要、来源和权利归属、授权场景、可出域范围、脱敏结果、地区/留存/访问/销毁要求。逐个登记模型权重、代码、工具和评测集的版本及许可证，确认权重使用与样品对外传输分别获准。 |
| 验收负责人 | 冻结产品及 lock 摘要、Release/Bundle、workflow/runtime、模型和工具版本。批准样品分层、各组合样本与重复数、冷/热态定义、并发档位、采样频率、时限、验收阈值及停止条件。空项保持待验证。 |

样品先使用批准的合成或脱敏单张 RGB 图。按图像尺寸、分辨率、目标数量、模型输入/输出长度与工具链分层，覆盖代表负载及获准上界。保存稳定样品 ID、摘要、分层及重复规则。标注、训练/评测隔离和独立真值只在获授权的 WP-05/06 质量评测中使用。[授权台账](../PLATFORM_GOAL.md#当前授权记录) · [依赖门禁](../../DEPENDENCIES.md)

## 2. 在目标机执行 RTX 4090 验收

1. 核对 GPU UUID、SKU、显存总量和基线占用，保存 OS、内核、驱动、驱动报告 CUDA 与容器内实际 CUDA 版本、容器运行时、Compose 配置摘要及镜像 digest。记录 Python、PyTorch、vLLM、Transformers、SAM3 或实际所选 vision 实现版本、模型权重摘要、精度/量化、批次与缓存配置，以及宿主库存和租约口径。采样器覆盖主机 PID namespace，并记录 PID、启动代际、容器/进程角色的关联。
2. 先测空载，再分别运行每个模型和视觉工具进程。冷态从确认旧 worker 已退出并记录文件缓存条件开始，分别计启动到就绪、就绪到首次推理完成及模型重载耗时。下载权重单独计时。热态用约定预热次数和已加载进程，记录稳定窗口内的延迟、吞吐及显存。
3. 用同一批样品依次验证单进程、共驻、单类并发和模型/工具混合并发。从单并发逐档升高，记录请求并发、实际活跃进程及放行与拒绝。对每档记录每个 PID 启动峰值、常驻和单次运行峰值，以及同一窗口内整卡实测峰值、最小空闲显存和采样间隔。整卡峰值直接取整卡采样最大值，不使用各进程峰值的和。可用时另存框架 allocator 的 allocated/reserved 峰值，用于解释短时分配；采样缺口及不可读值标 `UNVERIFIED`。用实测共驻峰值和批准的余量校核同一 GPU 的共享显存预算，以及常驻与运行槽位。
4. 在独立窗口执行已批准的工作进程超时、取消、崩溃、supervisor 重启和受控单 Worker OOM。分别标记实际 CUDA OOM、进程故障与准入拒绝。采集故障起点、进入 draining、守护回执、旧进程树与 GPU context 退出、新租约放行和首个健康样品成功的时间。旧持有者退出前验证容量保持占用，旧 token 无法释放后继租约。缺失可信退出见证时保持 draining，由宿主负责人按批准路径处理。恢复后复跑基线或最后一个合格档位，核查没有陈旧写入或残留占用。

采样使用宿主现有的 `nvidia-smi`。开跑前核对目标驱动的 `--help-query-gpu` 和 `--help-query-compute-apps`。批准 `GPU_UUID` 和 `SAMPLE_MS` 后，同时运行两条查询，记录 UTC 时间与命令退出码。若进程查询缺时间戳，由采集器在每次读取时加 UTC 时间。[NVIDIA 查询与采样文档](https://docs.nvidia.com/deploy/nvidia-smi/index.html)

```sh
TZ=UTC nvidia-smi -i "$GPU_UUID" --query-gpu=timestamp,uuid,memory.total,memory.used,utilization.gpu,temperature.gpu,power.draw --format=csv -lms "$SAMPLE_MS"
TZ=UTC nvidia-smi -i "$GPU_UUID" --query-compute-apps=gpu_uuid,pid,process_name,used_gpu_memory --format=csv -lms "$SAMPLE_MS"
```

## 3. 执行 remote-primary 验收

1. 在隔离项目核对真实 TLS 目标、可信端点描述摘要、显式 remote-primary 路由、实际版本证明、Binding 限额和项目权限。冷态记录客户端及 Worker 新启动后的首个请求，热态使用批准的稳定窗口。供应方未提供服务端冷态见证时，仅标记客户端冷态。先提交一个获准样品，经当前 fence 回读 Execution、Attempt、dispatch、ModelInvocation、实际身份版本来源、请求摘要、完整应答摘要和用量。响应 schema 拒绝、版本无法确认和回包截断应保留真实的失败或缺失状态。
2. 按获准档位逐步增加并发及负载。记录逻辑任务、每次物理尝试、应答和拒派。若已批准，验证 429、超时、取消、迟到回包、撤销与显式 fallback。优先使用厂商批准的测试窗口或故障接口，缺少条件的用例标 `RUNTIME_NOT_RUN`。每次 fallback 使用经独立评测的已批准路径，并保留触发 Invocation 与后继 Attempt。供应方实际在途额度只凭匹配 lease 和 dispatch 的可信终态证明结算，套接字关闭后无证明则保持 draining。
3. 核对成本、隐私与留存。凭据由宿主注入，仅在批准的端点出域。普通审计与测试日志保留许可范围内的 ID、状态、长度与摘要。经数据授权和宿主策略共同允许的完整、受限并通过验证的原始应答可进入受限证据存储，登记访问范围与留存期。原件不可保留时记录省略原因。按现有价格表估算每笔物理调用，并与供应方账单对账，重试和 fallback 全部计入，未知计费用量保留待核对。[HTTP 接入与审计约束](PLAN.md#调用审计与-worker-交接) · [资源额度与恢复](../../implementation_evidence/WP-04/W4.4_RESOURCES.md)

## 4. 指标、停止条件与验收

| 指标 | 计算口径 |
|---|---|
| 时延和恢复 | 端到端从受理到持久终态，队列等待从入队到开始，Provider 从实际派发到完整回包或终止。按冷/热态、并发档及样品分层报告 P50/P95 和有效样本数。单列各结果类别及超时、失败样本，报告故障到可信释放、重新准入到首个健康结果的实测时长。 |
| 吞吐与失败 | 吞吐为稳定观测窗口的完成任务数/秒。任务成功率为成功终态任务数/受理任务数。429、传输错误、超时及取消分别以对应的派发后尝试数/进入物理派发的尝试数计算。另列派发前取消、明确拒派与发送未知。报告结束时仍未终态的任务数和在途尝试数。 |
| 资源与成本 | 按 PID 及整卡记录实际采样峰值、空闲余量与样本数，区分实测、估算及不可用。报告总成本、计费尝试均价和每个受理任务成本，分别使用供应方费用总额/计费物理次数和费用总额/受理任务数。注明计费单位、币种及账单窗口。 |
| 质量 | 单列 WP-05/06 的标注评测，对每个指标给出真值分层和分母。召回使用标注目标数，漏检率使用标注违规样本数，误放率使用标注违规任务数，自动放行风险使用实际自动放行数。报告不确定或待复核比例与区间。零分母为未定义。 |

开跑记录必须填具可执行停止阈值及观察窗口，包括整卡最小空闲显存、温度或硬件告警、时延/队列积压、错误率、恢复时限及 Provider 速率、token 和费用。接近下一次发送可能超出预算时停止升档或派发。一旦触发阈值，或出现授权、端点、隐私、版本或证据边界违例，停止新派发，保留在途和现有证据，按已批准方式排空或终止。受控 OOM 仅在专门窗口按预案注入，并在首个预期故障后进入回收核验。任何恢复需满足已登记的健康、额度和停止解除条件，记录签核。

本地代码、真实设备/Provider 运行和标注质量分别签核。真实运行仅在环境、版本和样品与批准记录一致，全部必验用例达标且可追溯时标 `RUNTIME_VERIFIED`。环境未到位记 `RUNTIME_NOT_RUN`，已观察但证明不足记 `UNVERIFIED`，阈值失败记录失败及受影响配置。[技术架构 §3–5](../../../specs/04_Runtime_Technical_Architecture_V1.0.md) · [测试策略](../../TEST_STRATEGY.md)

### 容器重建与 PID namespace

容量账本的生命周期可能长于单个 Worker 容器。目标机验收需登记资源账本持有者所处 PID namespace、Linux boot ID 和守护进程代际，然后在独立验证环境重建 Worker。使用部署批准的稳定 PID namespace 时，检查仍能确定原执行树是否退出并关联其回执；只有证据匹配才可重新分配额度。若部署在重建时更换 namespace，须验证旧容量保留、告警可见及既定恢复路径，并记录需要的宿主处置。部署方确认最小权限方案和隔离影响后再在目标环境验证。当前为 UNVERIFIED。
