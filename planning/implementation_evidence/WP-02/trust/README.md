# WP-02 B2.4 Trust and Runtime capabilities

B2.4 implements local trust-policy enforcement, detached signature verification through an injected backend, and host capability checks. The isolated test verifier executes Ed25519 through the locally installed OpenSSL binary. Production policy, signing identities, provenance authority and key management require separate authorization.

## Code evidence

- `bundle/trust.py` resolves one current, immutable host snapshot per attempt. The manifest root must match the independently recomputed root. The host chooses the environment, policy, profile, source authorization and distinct-publisher quorum. Admission validates the signature registry, evidence SHA-256, key grant and SHA-256 public key pin, authoritative revocation state, verification instant and the backend result's exact claims. All attached signatures must verify. A missing snapshot, claim, evidence row or required source attestation fails closed. Source policy can also be checked before signing.
- `bundle/capabilities.py` checks the supported Bundle schema, numeric Runtime version range, required and explicit optional capabilities, exact installed implementation versions, features and pinned review evidence. It validates the configured model route and reuses the WP-01B `ReviewMetadata` and `validate_model_policies` for independent fallback evaluation and local-primary exceptions. Versioned Runtime protocol and workflow support come from the current host capability snapshot. These application inputs introduce no persisted schema or wire migration.
- The host is responsible for authenticating policy and capability snapshots and their review records. An opaque production cryptographic backend that verifies exact claims can implement `SignatureBackend`. The repository supplies the Ed25519 backend exclusively under the test fixtures. No production provider, signer, key store or provenance authority was configured.

## Approved isolated profile

Profile ID `jimu-wp02-test-ed25519-v1` is usable only in the `isolated_test` environment. The detached payload is exactly 64 raw Ed25519 signature bytes. The existing `DetachedSignatureRef` pins the registry, signature ID, signature version and SHA-256 of those bytes. The registry provides the signing key pin and claimed timestamp. Verification authenticates that metadata together with the root.

The signature input concatenates the following bytes in order.

1. ASCII prefix `b"JIMU\x00WP02\x00TEST-ED25519\x00V1\x00"`.
2. The recomputed root digest decoded to 32 bytes.
3. Each exact UTF-8 registry ID, signature ID, signature version, key ID and key version, in that order. Each string is prefixed with its byte length as an unsigned 32-bit big-endian integer.
4. The claimed signing instant as a signed 64-bit big-endian UNIX epoch time in UTC seconds. Fractional seconds are rejected.

A granted Ed25519 SPKI DER public key must have the exact SHA-256 named by the host key pin. The signing and verification instants both fall within the key's half-open validity window, and the signing instant cannot follow verification. A revocation effective at verification time rejects the signature, including when the package was signed earlier. An approved trust policy sets a minimum number of distinct authorized publishers. All attached signatures must pass and several keys belonging to one publisher count once.

`tests/fixtures/wp02/trust/public_vectors.json` stores an independently framed positive vector and a cryptographically valid signature covering a different root. The independent frame was computed with explicit hexadecimal domain bytes, integer encoding and fixed string fields outside the fixture implementation. The SHA-256 of the public vector file is `1b79cde12852f07169ffa7fc88691d0b2224dcebef12a64ff8f4b96894ae26ed`. The file contains the public key, preimages, signatures and their digests.

Ephemeral integration keys are generated by `openssl genpkey -algorithm Ed25519` into exclusive mode-0600 files in temporary directories and deleted in a `finally` block. Verification uses `openssl pkeyutl -verify -rawin -pubin -keyform DER`. Commands use fixed argument lists without a shell, a ten-second limit and an isolated OpenSSL configuration. No private key enters source, Bundle, logs or test output.
