# PRD｜从巡检需求创建到多设备场景运行

版本 0.1 · 产品评审稿 · 适用范围为单张 RGB 图像巡检。读者为产品负责人、需求运营、算法与工具研发、场景交付、Runtime 开发和测试负责人。

## 1. 产品目标与完成定义

需求人员能够创建一项违规检查，算法人员能补齐并复用所需能力；场景负责人能为同一场景的多个拍摄来源分别选择多项检查，导出一份独立 Bundle。运行负责人能让 Runtime 接纳、激活该包，用每个来源的实际图像执行对应算法。需求人员最终能在原检查项下看到结果、证据和使用的需求修订。

以一次交付验收这个产品：选择一版已发布场景，在 Web 上指出设备 A、B 各应检查什么；将导出的同一份包交给独立 Runtime；分别提交两个来源的图片；从每张图的结果反查确切版本、逐项义务、证据和缺口。运行期间无需向 Web 查询最新草稿或配置。

**本期边界。** 包含需求编写、能力补全、场景装配、发布交付、单图推理和结果回查。多设备表示一个场景接收多种拍摄来源，每次执行仍只处理一张图。跨摄像头融合、视频跟踪、模型训练、跨车或跨人证据归并、自动生产上线留至后续。首个实景仍可使用项目约定的非机动车停车；对象关系、设备路由与导出格式须可服务其他主体。

## 2. 现状与建设缺口

| 可以沿用 | 本期需要补齐 |
|---|---|
| Web 的对话创作和草稿预览、正式能力登记、算法修订发布、单卡 Build 与多卡联合计划 | 让草稿明确表达检查义务；按主体独立管理和复用 Question/Tool；补齐类型化输出、违规类别和确定性规则绑定 |
| Runtime 的六节点契约、Bundle 编译与来源校验、接纳和 Release 激活边界 | 把精确 Web Build 和场景配置转换成原生 Bundle；实现并验证可信来源选支、按原 Check 汇总和回查 |
| 单文件模拟器已演示来源矩阵、提示词组装、快照与逐节点数据 | 以实际作者服务、正式包、独立 Runtime 和经授权的模型/工具执行建立端到端证据 |

Web 的 Publication 证明算法修订已发布，Build 冻结该修订及其引用。Runtime Bundle 表达一版场景的可执行配置；Release 记录被接纳的 Bundle 在何处获准使用。它们各有自己的身份和状态。

## 3. 用户旅程与 P0 功能

| 步骤 / 责任人 | 用户操作 | 系统响应与完成条件 |
|---|---|---|
| F1 创建需求 · 需求人员 | 从业务现象创建算法卡草稿，选择或新建主体、Check 和违规类别，描述适用范围、判断单位、正反例及证据不足时的期望 | 可在能力尚不存在时保存。系统列出待澄清的业务口径和待补齐的工程能力，保留原需求入口 |
| F2 补全能力 · 算法/工具负责人 | 从主体目录引用已有 Question、Tool 和已登记模板，需要时创建新版本。配置发现、定位、联合观察及可选候选预测所需的模板和模型，定义主 Fact、工具输入输出、资源与失败行为 | 每项 Check 可见“需要哪个结果、谁生产、是否必需”。作者可以预览各用途的实际生效模板、变量来源、响应契约及失败路径。其他 Check 能复用同一能力版本。工程绑定与业务确认的责任人可追踪 |
| F3 发布算法修订 · 有发布权限者 | 核对 Check、类别、正式能力版本和判定口径，发布修订 | 取得不可变 Publication 与精确 Build。若作者端已发布而 Build 物化失败，显示已有回执、支持幂等恢复；场景只能装配已物化的精确 Build |
| F4 配置场景与设备 · 场景负责人 | 新建场景修订，把固定相机、移动巡拍等来源或设备档案列为行，把检查能力列为列；启用对应格子，绑定该来源的取证方式、定位档案和现场资源 | 预览每个来源的应检清单、有效主体、共享计算及独有资源。相同设备档案可复用；固定机位私有边界须匹配相机视角与标定版本 |
| F5 预检并导出 · 场景负责人 | 对指定场景修订预检，查看相对上一版的义务/策略差异，生成候选 Bundle | 输出可独立加载的原生包、摘要、版本和编译回执，可定位回 Build/Check。引用冲突或必需资产无生产路径时指出来源、Check、字段和修复入口。草稿及已发布 Build 保留 |
| F6 接纳与试运行 · 运行负责人 | 导入导出原件，验证兼容性和来源，创建并按权限激活测试 Release，提交图片和可信来源上下文 | 接纳失败有原因；未激活不得进入正常任务路由。在途任务锁定原 Release、Bundle 摘要和运行依赖，后续发布不改写历史 |
| F7 回查与修订 · 需求/场景负责人 | 从一张图查看所有应检项，或从原 Check 查某次执行。发现误判时引用对应证据发起新修订 | 展示违规类别、逐 Check 状态、命中观察组、证据、缺口、来源及版本。对不同项目按权限查询。结果同步失败能按执行身份重试，重复交付不会产生重复结论 |

**Web 交互落点。** 在现有创作工作区完成 F1，在能力登记区完成 F2，从算法发布进入 F3。在现有 Build 视图后增加场景装配与交付入口承载 F4–F5。F6 返回明确的接纳/激活回执。F7 由执行记录链接回原卡的精确修订，并同时提供从原卡查看运行记录的入口。

## 4. 配置由谁填写

| 权威来源 | 应维护的内容 |
|---|---|
| Web 需求与能力库 | 主体、稳定类别编码、Check 修订、证据用途及必需性。正式 Question、Tool、提示词模板及片段、JEV 槽位映射、Grounding 档案、Question 主 Fact、工具输出与 Rule 绑定。首版建议一项原子 Check 对应一个主类别，多项 Check 可归属同一类别 |
| 场景配置 | 场景 ID；可信来源匹配键；每个来源启用的算法能力和 Checks；选用的模型、定位及分组档案；设备视角、区域资源和坐标变换。精确版本可由选取正式资产时自动带入 |
| 导出器 | 展开依赖、去重、校验兼容、生成各来源节点加载索引与原生资产；冻结版本、摘要与逐 Check 映射。运行必需资源和映射受包完整性保护。凭据在部署环境管理 |
| 单次运行 | 请求图片、实际场景与设备来源、上下文快照、实际使用的模型/工具版本、观察组、调用 Attempt、有效 Facts 和 Decision |

共用一次计算的前提是输入、主体与观察粒度、模板/模型、权限和资源版本相容。单个 Check 的证据义务及追溯关系在共享后仍单独保存。导出器不得从自由文本猜测规则、把未支持的模型槽位当作可用，或通过删减应检项使预检通过。

### 4.1 提示词资产的登记、绑定与预览

参照 Question 的管理方式，算法人员可以保存待补全草稿、发布正式模板版本、在兼容的绑定中复用，并查看引用该版本的 Profile、Question、RuleSet、Check、Build 与场景来源。修改模板正文、片段、变量契约或响应契约时发布新模板版本，需要采用时由消费者显式更新其精确引用。已冻结的 Build、Bundle 和 Release 保留原版本。

| 作者需确认 | 发布与预检要求 |
|---|---|
| 身份、用途、适用范围 | 记录稳定 ID、版本、`schema_version`、用途及适用主体/场景。可执行模板的 `purpose` 枚举为 `profile_discovery`、`object_grounding`、`object_observation`、`candidate_prediction`。版本与摘要通过精确引用锁定 |
| 模板正文、变量与片段 | 正文有长度限制，仅使用已登记的命名占位符。每一变量声明名称、来源、字段路径、Schema、必需性及缺值策略。允许来源为 `context`、`profile_metadata`、`question_metadata`、`object_geometry`、`image_reference`，路径须为对应契约及 allowlist 所允许；Question 仅可见自身获准的上下文。片段使用精确引用，依赖无环，并按确定顺序展开 |
| 渲染和预览 | 用确定性的 `literal_substitution` 替换占位符。必需变量缺失时阻止渲染，可选变量仅按声明省略占位符。禁止表达式、循环、条件、外链加载、动态导入和凭据变量。编辑器以给定样例显示实际片段顺序、变量来源、缺值处理、渲染结果与响应约束 |
| 响应 Schema 和 ModelBinding | 模板固定生成的响应 Schema，模型绑定须核对用途、输入输出类型与模态能力，同时固定 Provider、部署约束、资源预算和失败/Fallback 策略。模型返回须经 Schema 与节点身份校验。重试或换模型须符合显式策略，兼容且已独立评估的 Fallback 才能生效 |
| 发布与交付 | 导出器展开模板、依赖片段、Schema、绑定和策略，按精确身份去重并检查用途、兼容性、变量权限、依赖环和必需生产路径。运行资产及 Check 来源映射受 Bundle 完整性保护，接纳端独立校验。凭据从运行环境获取。调用记录保留实际模型、已用契约和证据，失败于调用前的记录不生成 ModelInvocation |

### 4.2 各节点的提示词与 Check 片段

| 使用处 | 作者填写与绑定 | 输出、失败与职责边界 |
|---|---|---|
| N02 主体发现 · `profile_discovery` | 主体发现模板通过 Profile 的发现绑定引用。文本模式可组合合格 Profile 的主体片段与审核通过的 Check 片段。固定模型模式则经有类型的已登记槽位映射归一化输出，预检验证实际部署、Schema 和槽位兼容性 | 只返回已登记且通过前置资格检查的 Profile 命中，以及配置允许的选题建议，不返回实例框、Object ID 或违规结果。整份发现响应无效时记录失败，零命中保留发现覆盖缺口。固定槽位映射只消费模型已支持的槽位 |
| N02 可选筛题 · `optional_question_proposal` 调用用途 | `QuestionSelectionPolicy` 明确必选及可选 Question、顺序及失败路径。首版建议 `all_declared`。`model_advisory` 优先用 `shared_n02` 在发现绑定内承载提案；`explicit_additional` 须单独获批，固定兼容发现的绑定、提案 Schema、审查、资源和含重试的调用上限 | 该用途属于调用审计，使用 `profile_discovery` 模板及兼容绑定。模型只能建议已登记的可选项，必选项由系统保留。可靠的 Profile 命中伴随无效提案时按固定策略纳入全部可选项或阻止该 Profile；整份发现失败时不生成命中。只有显式追加调用实际发出才生成独立调用及 Attempt |
| N03 定位 · `object_grounding` | 为 Profile 选择模型定位绑定及模板，定义目标与取景范围，固定定位响应 Schema 和坐标约束。选用 Tool 定位时登记明确的 Tool 绑定及输入映射 | 独立定位每个已命中 Profile，校验原图像素 XYXY 与变换来源，继承 N02 锁定的 Question 集合。分别记录未找到目标、定位失败与部分完成。纯 Tool 定位保留 ToolExecution，并以其记录定位来源 |
| N04 联合观察 · `object_observation` | 每项 Question 引用兼容自身唯一主 Fact 的模板和分题响应契约。Profile 观察绑定固定联合响应信封；版本化编译器按同一 Object 的有效 Question 集合生成一次联合提示及按精确 Question 身份索引的响应 Schema，保留编译器版本、派生 Schema 摘要和请求证据 | 正常路径每 Object 发出一个联合请求。整批传输或信封解析失败保留 Attempt，且无新 Fact；分题无效生成该题 `error`，仅在信封与关联可信时保留有效同批结果；看不清为 `unknown`，由配置或上下文证实不适用才可用 `not_applicable`。重试是锁定原选题集合的新整批 Attempt |
| N06 候选预测 · `candidate_prediction` | RuleSet 可绑定候选模板、已登记类别及带类别引用/分值的响应 Schema | 候选输出仅用于排序并留存实际调用。关闭、空结果或失败时，适用性检查与全部必查 Rule 扫描照常执行；Decision 来自确定性规则和有效证据 |
| Check 的可选 JEV 片段 | 作者在精确 Check 修订中引用经审核、版本和摘要锁定的 `profile_discovery` 片段，声明适用主体及发现意图。导出器仅为已启用 Check 和匹配 Profile 展开片段，按声明顺序稳定合并，重复引用去重且保留来源映射。固定槽位模式展示实际槽位，另行标明文本片段未参与运行 | 片段只提供发现线索。变量、Schema、模型能力与长度限制同主模板；缺失及冲突定位至来源、Check 和片段版本。业务适用性、证据必需性、类别和判定留在各自的类型化配置中 |

N01 由可信来源与上下文配置驱动。N05 执行预绑定的 ToolPlan，Tool 内如需模型，仅可通过显式 `vision_auxiliary` 绑定，按 Tool IO 和调用身份审计。该能力不增加新的 `PromptTemplateDefinition.purpose`；若启用模板，沿用目的兼容性和输入输出校验。作者端对话、草稿辅助和离线模拟页的文本均属于作者工具。只有通过模板登记、编译和 Bundle 接纳的正式资产才进入 Runtime；模拟页的预置响应和教学 JSON 用于走查。

## 5. Runtime 的六节点消费契约

| 节点 | 从 Bundle 与本次输入中解析什么 | 可供验收的输出 |
|---|---|---|
| N01 接入及前置选支 | 场景 ID、已锁定 Release、可信设备来源与上下文。N01 形成快照，工作流在进入 N02 前唯一选择来源配置并执行 Profile 资格检查 | 已选来源和依据、已解锁能力及类别、应检 Checks、合格/排除/未决 Profiles。未知来源、匹配歧义、缺字段各自有原因 |
| N02 JEV 路由 | 仅为前置检查合格的 Profiles 加载已绑定的发现模板及片段，或按固定模型的槽位映射消费输出。按冻结的选题策略记录有效 Question 集合 | 命中哪些主体/Profiles、服务哪些检查、有效 Questions 和发现缺口；无实例框 |
| N03 Grounding | 对命中主体加载对应定位提示与能力，依来源档案应用定位或分组策略 | 原图坐标、观察组 object_ref、标记图与定位来源。相同工作项分别交给 N04/N05 |
| N04 联合观察 | 继承 N02 为当前 Object 所属 Profile 固定的有效 Questions，按契约组成一次正常路径的组内联合请求 | 分题校验的主 Facts、观察组引用、模型调用及失败记录 |
| N05 工具核验 | 取当前主体且为已启用 Checks 所需的 ToolPlan，显式绑定输入、资源、步骤依赖与输出 | 每组 Tool Facts、实际测量对象、坐标/单位及工具证据。仅依赖 N03 输入的步骤可与 N04 并行 |
| N06 逐项判定 | 按执行及观察组汇合证据，对适用的 mandatory Rules 全扫；预测候选可辅助排序，所有有效命中保留 | 按 Check、观察组和类别返回判定与缺口。整图类别可去重，原 Check 与 Rule 仍可逐一回查 |

## 6. 用户必须能分辨的三类异常

- **配置期缺口。** 已选择的必查能力无可用工具绑定、规则没有 Fact 生产者、固定 JEV 槽位不存在、两种来源匹配条件重叠。预检拒绝生成可交付候选并定位责任项；已有可用 Release 继续有效。
- **接入期不匹配。** 场景或设备不受该 Release 支持，或必要识别信息不可信。保留请求与具体原因，下游不产生虚构的模型记录。
- **运行期证据缺口。** 来源明确未配置的 Check 标为“未配置”；有依据排除的为“不适用”；应执行但缺证据的为“不确定/未完成”。N02 无命中或定位为空不能推出无违规。已有一项有效违规则保留，同时报告未覆盖的其他义务。

## 7. 交付验收

验收资料同时保留输入、快照、观察结果与预先确定的期望。示例矩阵可用任意获准的巡检场景：检查甲和乙共用一项已登记能力，固定来源启用甲、乙，巡拍只启用甲。为每个来源各准备与设备及视角真实对应的图像。

| 编号 | 验收动作 | 通过条件与证据 |
|---|---|---|
| A1 | 从空草稿创建甲、乙，登记一次共享能力，发布并组装 | 先保存缺少生产者的需求并显示责任人；补入同名但 Fact 类型不兼容的工具时仍提示缺口，补入兼容版本后原需求通过复检。两份 Check 引用同一精确能力版本；草稿、发布修订、Build 和场景修订可互查。升级共享能力能列出消费者，旧 Build 不变 |
| A2 | 导出上述场景，交给独立 Runtime，暂停对作者服务的访问 | 仅凭包、受信运行环境及已登记依赖即可完成接纳与解析；导出回执与接纳回执的 Bundle 摘要一致；修改包内容后接纳失败 |
| A3 | 同一 Release 下分别提交固定来源、巡拍来源的请求 | 两次任务分别承担两项/一项检查。Trace 可见 N02 实际片段或槽位、N03 实际定位模板、N04/N05 同组身份，以及 N06 原 Check 引用 |
| A4 | 分别注入配置缺口、运行时工具故障、未知来源、JEV 无命中 | 设置缺口得到可修复的预检诊断；工具故障只影响依赖它的检查；未知来源留下接入原因；无命中保留覆盖缺口。均不误报完整无违规 |
| A5 | 修改提示词或设备矩阵，导出并激活新版本，再查看旧执行 | 新执行采用新版本；在途任务完成时仍引用旧摘要；旧执行回查保持原 Build、Release、Bundle、来源、模板/Schema、实际模型、Rule 和证据。重复提交交付命令或结果回执可安全对账 |
| A6 | 使用真实 Web 发布与导出、真实 Runtime、经授权的实际模型及工具，分别执行两种拍摄来源并回查 | 每项结果能从 Web 回到实际 Execution、原图、实际调用与证据，再反查原需求修订。验收集中包含有预期命中的样本和完整负例；逐项核对记录差异 |
| A7 | 登记、预览、导出并独立核验各用途模板与 Check 片段 | 可预览各来源采用的模板、片段或槽位、类型化变量与 Schema。确认相同输入按同一顺序产生相同渲染结果；分别注入未登记变量、越权路径、必需变量缺失、片段环、用途/Schema 不兼容和包内容篡改，分别在预检、渲染或接纳阶段阻止并留下可定位诊断。可选值缺失按声明省略 |
| A8 | 用确定性 fixture 验证发现、定位、联合观察与候选失败路径 | 只装配启用 Check 且通过资格检查的 Profile；无效筛题建议触发锁定的失败策略并保有必选项或阻止该 Profile；定位失败保留缺口；正常路径每 Object 一个联合调用，分题无效与整批失败分别留证；空候选或预测失败时，适用必查 Rules 仍全部检查 |

**验收分层。** 浏览器模拟器用于需求走查；确定性 fixture 用于配置和接口集成回归；A6 是“完整实际运行”的交付门槛。单次现场贯通不证明普遍识别质量。业务质量验收另冻结代表性标注集、按来源和类别的指标、门槛及负责人。真实设备、数据、模型端点和调用额度由有权限者提供，本 PRD 不代授生产或付费调用权限。

## 8. 交付顺序及评审决定

1. **先跑通作者到交付。** 建立两项正式 Check、来源矩阵、精确 Build 输入、提示词资产、适配与预检，导出第一个原生候选包。以 A1/A2/A7 为交付门槛。
2. **再跑通执行与回查。** 在隔离环境完成来源选支、六节点加载、逐 Check 汇总、历史版本与回执重试，以 A3–A5/A8 验证。
3. **最后验真实链路。** 冻结测试环境、设备清单、样本及期望，以 A6 形成实景贯通记录，再按单独约定做质量与生产验收。

评审时建议拍板三件事：谁有权定义类别及接受 Check 的业务含义；同一场景各来源必须承担哪些 Check、哪些差异允许显式配置；由谁提供哪两类实拍设备、测试环境与独立验收样本。角色命名、菜单布局、JSON 键名等实现细节另入技术规格。
